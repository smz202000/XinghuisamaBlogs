## 先分清连接故障和模型故障

昨天处理 QQ 机器人不回复，最初看到的是 NapCat 到 AstrBot 的反向 WebSocket 连续报错：`connect ECONNREFUSED 172.18.0.1:6199`，每 5 秒重试一次。容器里 `host.docker.internal` 能解析到 `172.18.0.1`，但这个地址上的 6199 当时没有 AstrBot 进程监听。先查容器状态和日志，再看主机端口，避免把“机器人没回话”一股脑归因到模型。

AstrBot 4.29.3 启动后，6199、6185 和本机的 7833 都恢复监听。更关键的回归不是端口，而是实际 QQ 消息：日志里出现 OneBot v11 适配器已连接，收到“你谁啊”后也生成并发送了角色回复。Qzone 自动绑定仍有 Cookie 警告，但它是旁支问题，不该误判成整条 QQ 消息链都坏了。

## 配置写进去了，不等于服务能用

为了试验带图片输入的 GPT 模型，我把 provider、主模型和自学习插件的模型 ID 改成 `worldcodes-gpt-4o-mini`，并将模态设为 `text`、`image`。改自学习 JSON 时，Python 首次读取报 `JSONDecodeError: Unexpected UTF-8 BOM`。原因是 AstrBot 写出的配置带 BOM；读取时改用 `encoding='utf-8-sig'`，再以普通 UTF-8 保存，JSON 校验通过。

随后真正的模型请求返回 HTTP 403。这个结果说明仅修改 provider 字段和通过 JSON 校验，不代表上游账号有权限使用该模型。再切换另一种模型后，出站服务仍不可用，于是停止在配置层反复试错，恢复此前备份的 DeepSeek 方案：将 `cmd_config.json` 还原为 `cmd_config.json.20261026-131305`，并把自学习的筛选、提炼、强化 Provider 都设回 `worldcodes-deepseek-v4.1-flash-1017`。

## 用用户路径做最后验证

恢复后重启 `astrbot run --port 6185`，确认 AstrBot WebUI 与 OneBot 端口监听，并从 QQ 收到实际回复。排障留下的做法很朴素：先证实链路，再验证模型请求；备份先行；最后沿真实消息路径回归。模型接口的 403 也要如实记下，不能用“服务已启动”冒充模型已打通。
