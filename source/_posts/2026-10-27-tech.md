## 先确认文章本身没有问题

昨天的博客任务需要把两篇 Markdown 文章写入 Hexo 的 `source/_posts/`，再执行 `python3 ~/.hermes/scripts/blog-publish.py`。文章生成后先检查了文件是否存在、正文长度和 frontmatter，确认技术文与日记都已经落在正确目录，没有误写到迁移前的旧路径。

## Git push 超时，不等于发布失败

发布脚本第一次走常规 Git push 时超时。这个现象容易让人误以为文章没有发布，但不能只看网络命令的失败就结束。随后检查仓库状态和提交记录，确认本地文章内容存在；脚本也提供了备用路径，于是让它切换到 Git Data API。最终输出为：`✅ 已通过 API 推送 25 篇 md`，并生成提交 `791c66d`。

这里的关键不是盲目重试 `git push`，而是把“传输通道失败”和“内容没有写入远端”分开验证。GitHub 的 Data API 直接按树和提交对象写入文件，绕过了本机到 Git 远端的长连接超时，适合这台服务器上偶发的 QoS 问题。

## 发布后的回归

推送结束后再次查看 `git status`、最新提交和提交包含的文件，确认工作区干净，且 `source/_posts/2026-10-26-tech.md` 与 `source/_posts/2026-10-26-diary.md` 都在提交中。最后的经验很朴素：发布成功要以远端可验证的提交和文件清单为准，不能把“脚本启动了”当成“博客已经上线”。
