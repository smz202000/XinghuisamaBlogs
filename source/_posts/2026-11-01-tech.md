## 先盘点，再动删除

昨天处理的是 NapCat 清理。目标不是“顺手删掉几个名字”，而是确认容器、镜像、挂载目录和监听端口分别属于什么。排查后确认：容器名是 `napcat`，镜像是 `mlikiowa/napcat-docker:latest`，宿主机数据目录是 `/home/admin/napcat-data`，约 1.5GB；容器还映射了 `127.0.0.1:3001` 和 `0.0.0.0:6099`。先做这一步，才能避免误删 Docker 服务或其他 Hermes 数据。

使用的核验命令包括：

```bash
sudo -n docker ps --format '{{.ID}}\t{{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
ss -ltnp | grep -E ':(3001|6099)'
find /home/admin/napcat-data -maxdepth 4 -type f | sort
```

## 破坏性操作会被拦截

第一次把容器、镜像和目录放在一条命令里删除时，系统的破坏性操作审批没有通过，命令实际没有执行。得到这个结果后，不能把“超时”误判成“已经删除”，也不能无止境重试同一条高风险命令。用户明确确认后，分步执行：`docker rm -f napcat` 成功，镜像也被移除，3001 和 6099 端口释放。

但数据目录随后暴露出第二个问题：直接 `rm -rf /home/admin/napcat-data` 时，部分文件属于容器内的其他用户，当前用户没有权限删除；使用 `sudo` 的后续清理又再次触发审批拦截。因此最终状态必须如实写成：容器和镜像已删除，端口已释放，但 `/home/admin/napcat-data` 仍有残留，不能把“服务停止”说成“数据清空”。

这次排障的关键不是一条神奇命令，而是把资源范围、审批状态、权限错误和最终状态分开记录。删除类任务尤其要以回读结果为准：容器列表、镜像列表、目录存在性和端口监听，缺一项都不能宣称清理完成。
